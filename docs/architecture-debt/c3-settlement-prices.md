# C3 · 白话档案：算战绩的股价有两套，三家各记各的，一家压根没管

**状态**：待做（第 3 批）
**来源**：2026-11-21 架构评审侦察通道 2
**关联**：incident 054（PR #607 刚收口）· track-record 口径混用史（盘面价 vs 复权价）

## 一句话

结算战绩要用历史股价。历史股价有两种：**原始价**（看着便宜，因为除权除息过）和**复权价**（把分红送股调整回去的，才算得出真实涨跌）。**用哪种的决定，现在是每个用的人自己记**——三家各记各的，还有一家压根没管。

## 现在长什么样

数据入口是 `fetch_kline(代码, 天数, 复权方式)`——「用哪种价」被甩给了每个调用方：

| 调用方 | 它记的 |
|---|---|
| `marking.py`（盯市） | 没传 → 拿原始价 |
| `job.py`（horizon 判定） | 自己传了「结算专用复权」→ 复权价 |
| `settle.py`（旧路径） | **压根没管** |

另外：

- 去哪家网站拿价（新浪/东财/腾讯）的逻辑全部藏在 `akshare_client.py:1393-1454` 的私有方法里。
- 有两三个小工具函数（日期归一、找基准收盘）在 `settle.py` / `judgment.py` / `marking.py` 里**各抄了一份**。
- 测试造假要模仿**中文列名**的假数据——中文列名成了隐形接口的一部分。

## 已经造成的麻烦

- 口径拿错 → 收益算错 → 战绩页读数错。这类混用已复发多次。
- incident 054 刚修过一次（PR #607：结算复权价锁死新浪 + fail-closed + 基准只和相邻真实收盘配对）——但修的是「点」，下次换个调用方还可能拿错。

## 打算怎么修

做一个统一的「拿价入口」：

- `settlement_series(代码)` —— 拿**结算专用**的复权价序列，口径内部定死。
- `reference_price(代码, 日期)` —— 拿基准价（如沪深300 对齐收盘），配对逻辑内部收编。
- 想拿错都拿不到：调用方根本不接触「复权方式」这个参数。
- #607 的 fail-closed 逻辑（新浪锁定）原样收编进入口，不丢。

## 好处（白话）

- 口径错误从「每次撞上再修」变成「代码上无法表达」。
- 测试不用再模仿中文列名——造一个假入口就行。
- 三处重复的小工具函数归一。

## 牵涉文件

`data/akshare_client.py`（取源逻辑收编）、`outcome/track_record/{job,marking,judgment}.py`、`outcome/settle.py`、openspec（结算口径契约）。

## 坑与注意事项

- 走 OpenSpec delta：结算口径现在散在实现里，要立成契约。
- #607 是刚收口的事故修复——收编时**逐行对照**，别把 fail-closed 的保守行为弄丢。
- 新浪锁定意味着单源依赖，入口要保留 fail-closed 语义（拿不到就不结，别悄悄换源）。
