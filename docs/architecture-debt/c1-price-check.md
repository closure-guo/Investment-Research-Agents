# C1 · 白话档案：查价格的程序像打地鼠，7 周打了 12 次补丁

**状态**：待做（第 5 批，先改 spec 粒度再实施）
**来源**：2026-11-21 架构评审侦察通道 1
**关联**：#254 / #337 / #566 / #579 / #582 / #599（六连补丁）· openspec/specs/price-level-tooling

## 一句话

系统有个程序专门检查 LLM 写的价格数字有没有乱编。它的做法是**黑名单**：遇到「长得像价格其实不是」的东西，就往黑名单加一条。**7 周 16 次提交里 12 次是修误报**——黑名单永远加不完。

## 现在长什么样

黑名单一族（全在 `metrics/decision_price_check.py`，806 行）：

- ~50 个「不是价格」的关键词、39 个字符的后缀表、15 个说明性短语、30 条别名、5 组日期正则、3 组枚举正则……共 **10 张互不统一的表**。
- 核心判定就是一句话：**「没被黑名单拦住的裸数字 = 价格」**。

被打过的地鼠（每次一个新语境）：`2026Q3`（季报记号）、`T+N`、`beta 0.9`（阈值）、`×乘号`、`编号列表 1.`、`PEG 2.07`、`覆盖比率 90%`、`带边舍入 0.01`、跨分句的方向词……

**每修一次要改三处**：openspec 规范（每条豁免逐条写成 requirement）+ 代码正则 + 测试类（22 个测试类里约 12 个以事故命名）。

## 已经造成的麻烦

- 误报会**阻断分析产出**（风险门禁打回），每次都要人工归因终裁（`tests/validation/` 有对照表，结论多为「校验器缺口，零真幻觉」）。
- 调试误报要拿生产 trace 原文重跑校验器（代码注释里 8 处引用 trace id 实证此事）——因为「文本承诺了哪些价」这个中间结果不落盘，看不见。

## 打算怎么修

换思路，两步：

1. **先分类，再判断**：新写一个「数字归类器」——拿到一个数字，先判断它是什么（价格 / 百分比 / 比例 / 天数 / 日期 / 序号 / 指数点位……），归类对了自然就不是价格。10 张表全部收进归类器内部当规则。黑名单里一大半条目就不需要了。
2. **先记账，再核对**：把「文本承诺了哪些价」先输出成一份**账本**（哪个数字、在原文哪个位置、跟着哪个方向词），再拿账本去核对。账本落进 trace——以后查误报看账本就行，不用重跑。

## 好处（白话）

- 打地鼠变成「归类表加一行」——新语境不再是新事故。
- 每条豁免三处同步 → 归类器一处。
- 误报归因从重放调试 → 看 trace 里的账本。

## 牵涉文件

`metrics/decision_price_check.py`（806 行，主战场）、`nodes/risk.py:568-679`（调用方 + 恶化判据）、`openspec/specs/price-level-tooling/spec.md`（豁免条目逐条入册的现状要改）、`tests/metrics/test_decision_price_check.py`（91 个测试）。

## 坑与注意事项

- **先走 OpenSpec delta**：现在 spec 是按 token 一条条记豁免（每条带 scenario），会随误报无限增长。要先把契约从「豁免清单」换成「归类契约」——行为不变，粒度换掉。这是它排第 5 批的原因。
- `risk.py` 的恶化判据现在用「摘录片段 ±24 字符」做集合运算——换账本位置时门禁逻辑要同步改，否则门禁判定会漂。
- 归类器上线初期新旧并行灰度，误报率数字要分桶归因后才能动 prompt/规则（incident 026 纪律）。
