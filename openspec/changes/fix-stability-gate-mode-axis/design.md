# Design: fix-stability-gate-mode-axis

## Approach

核心判断：**当日 `selection_mode` 在资格判定时点并非未知，只是被放错了查找位置。**
`run_screening_batch` 在 L2 打分前就已确定 `selection_mode`（因子路径是否可打分的判定先于
L2），并最终传给 `record_screening_batch` 落库——缺陷仅在于 `days_in_top_recent` 不接收它，
而是回头查一张此时必然还没有当日行的表。

修法：给 `days_in_top_recent` / `eligible_for_selection` 加显式 `mode` 入参；调用方提供时
直接以它作为 `as_of` 轴模式（跳过批次行查找），不提供时保持既有「批次行查找 → 缺失退全轴」
路径（带外兼容）。`pipeline.py:459` 精选池计算处传入当日 `selection_mode`。零 schema 变更、
零写入时序变更、「批次 ok 与池同生共死」单事务不变量不动。

生产验证锚点（复现证据，供测试用例取材）：10-27 实际入池 600150/600176（混合轴各 4 命中），
而因子口径 5 只命中 3 次的标的（002033/600916/601868/601901/603568）被混合轴挡住——修复后
该形态应翻转。

## Alternatives Considered

- **批次行先落 running 态（带 mode）**：写入时序倒置会留下「批次 running 但进程死了」的僵尸行
  ——恰是 issue #455 三连发（2026-10-21~23）修掉的故障家族；running-skip 规则会挡住启动补跑，
  6h 窗内无人接管。还要拆掉「批次 ok 与池同生共死」的 fail-closed 不变量。收益为零（mode 本就
  在内存里），纯增风险，不选。
- **落库后重算资格的后置修复作业**：池行先按错误口径落、再由第二个作业按正确口径改写——引入
  一段「池内容不可信」的中间态，监控/池分析消费方（16:22 自动池分析）可能读到错误行；复杂度高
  且治标，不选。
- **维持现状（接受混合轴）**：混合轴当前恰好「加速」池子恢复（fallback 日也计数），但代价是
  语义不可解释（池成员口径取决于批次落库顺序而非规范），且因子股门槛被流动性天数系统性稀释
  ——10-27 五只合格因子票全部被挡即是实证。规范是唯一真相来源，不选。

## Risks

- **归档顺序依赖**：`update-stability-gate-rolling-window` 与本 delta 同改「在榜稳定性门槛」，
  前者已合并待归档。处置：先归档前者，本 delta 归档时按 sync 后主规范全文重写 MODIFIED 块
  （prediction-pool-integrity 已验证的 drift 处置法）；proposal Impact 已写明。
- **行为翻转的观察预期管理**：修复后首日池成员与 10-26/10-27 的直觉不同（可能「变小」），那是
  正确口径的呈现而非回归——人工验证报告须按同模式口径逐只核对，不以「池变大」为通过标准。
- **缺省参数的静默 misuse**：新代码若忘记传 `mode` 会静默走回旧降级路径。对策：调用点只有
  pipeline 一处（全仓唯一），测试用例直接钉死日批路径显式传参；`mode` 入参校验非法值
  fail loud（与 `pool` 参数同风格）。
