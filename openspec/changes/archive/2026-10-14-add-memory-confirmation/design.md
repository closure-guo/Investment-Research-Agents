# Design: add-memory-confirmation

## Context

`memory/semantic.py` 已有完整的数据面与状态机：`list_clauses(status=...)`、`list_pending_clauses()`、`list_confirmed_clauses()`、`confirm_clause(id)`、`reject_clause(id)`（幂等、未知 id 返回 False），以及「注入仅 `confirmed`」的既有保证。缺的只是**暴露给人**：API 包装 + 界面。

页面形态：设计系统已交付 `PageShellC`（审批队列：左列表 + 右详情 + 确认/驳回动作）——本页正是该壳的目标场景之一（unify-ui-design-system proposal 的 7 页面愿景明列「记忆确认」）。

## Decisions

- **API 三端点，零业务复制**：端点只做「参数校验 + 调既有函数 + 404/幂等语义翻译」；`confirm_clause` 返回 False → 404（未知条款），True → 200（含幂等重复确认）。
- **状态过滤走查询参数**（`?status=`），默认 `pending`（审批队列的默认视图 = 待办）。
- **页面用 PageShellC**：左列条款（正文摘要 + 提炼时间 + 来源），右侧详情（完整正文 + 来源决策/结算样本 + 确认/驳回按钮）；AiBadge 标注「由模型提炼，仅供参考」；StatusBadge 三态（待确认/已确认/已驳回）。
- **入口同源**：侧边栏折叠图标（`aria-label="记忆"`）+ 命令面板项——与选股池/战绩页同模式。
- **不做编辑**：条款是「确认或驳回」的二元决策；编辑会让「LLM 提炼 → 人工把关」的溯源语义模糊。

## Alternatives Considered

- **把确认放进设置页**：放弃——审批队列是日常操作面（有 7 页面愿景的独立页定位），且 PageShellC 专为此形态设计。
- **CLI 脚本确认**：放弃——规范要求的是「人工确认」的可操作入口，界面是最低摩擦路径；脚本可作为运维兜底但不满足产品面。
- **支持批量确认**：暂缓——候选条款量级为月批 5-20 条，逐条确认（含阅读正文）符合「人工把关」的意图；批量易滑向形式化。

## Risks

- 页面长期空态（月批未接线前无候选条款）：**预期**——空态文案如实说明「等待月批提炼（当前未接线，见 issue #327）」。
- 确认操作直接影响风控辩论注入：属规范既有语义，页面需在按钮旁明示后果（「确认后即刻生效注入风控辩论」）。
