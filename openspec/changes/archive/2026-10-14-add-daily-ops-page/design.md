# Design: add-daily-ops-page

## Context

既有数据面：`GET /api/ops/jobs`（全部任务：排程 / 下次触发 / 最近运行 / 摘要 / 错误，add-eval-ops-console 契约）+ 手动补跑端点（`POST /api/ops/jobs/{id}/run`，含 409 已在运行与 cohort 关闭语义）；选股批次表（`screening_batches`：status/error/起止时间/各层计数/池数）已有数据但无历史查询函数。本页是**聚合视图**：不新增执行能力，只把当日状态按时间线呈现 + 提供补跑快捷。

页面形态：PageShellD（批次列表 + 步骤级状态图标）——设计系统四壳之一，正是「运行记录页」的目标场景。

## Decisions

- **时间线数据驱动**：从 `/api/ops/jobs` 的排程时刻排序渲染（15:30 快照 → 15:40 选股 → 15:45 因子监控 → 16:00 判定 → 16:10 执行 → 16:20 仿真结算 → 16:30 盯市 → 16:35 指标快照 → 16:40 完整性 → 18:00 cohort），**不硬编码任务清单**——未来新增/调整任务自动跟随。
- **步骤级状态图标**：成功 / 失败 / 未跑（今日无运行行且已过排程时刻）/ 运行中 / 跳过（skipped-disabled）五态映射 StatusBadge（active/failed/retired/running/degraded）。
- **失败原因逐字**：job 的 `error` 字段与选股批次 `error` 原样展示，不改写不归类。
- **补跑复用既有端点**：一键补跑 = `POST /api/ops/jobs/{id}/run`；409（已在运行）与 cohort 关闭语义按端点返回值如实提示。
- **与评估运维页分工**：本页只读聚合 + 补跑；配置类（cohort 时刻/开关、回测、健康检查、预登记）留在评估运维页，本页提供跳转。
- **选股批次历史**：`list_batches(limit)` 读函数（按 trade_date 倒序），默认近 20 批次。

## Alternatives Considered

- **把本页并入评估运维页签**：放弃——7 页面愿景要求独立「日批运维」页；且「当日一眼看全」与「全量控制台」的信息架构不同（前者时间线叙事，后者表单操作）。
- **时间线硬编码 10 个任务**：放弃——注册表已扩容 3 次（5→8→9→10），硬编码必然漂移；数据驱动零维护。
- **页面内直接展示 cohort 配置表单**：放弃——重复评估运维页且违反「本页只读聚合」定位。

## Risks

- 快照封禁期多数任务为失败/未跑态：**预期**——页面如实呈现（这正是本页价值：让「今天什么没跑」一眼可见）。
- 一键补跑在快照缺失时会失败（预期）：失败原因逐字回显，不掩盖。
