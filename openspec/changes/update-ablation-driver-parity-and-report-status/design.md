# Design: update-ablation-driver-parity-and-report-status

## Approach

三件事，按「先止血、再堵漏、后立规」排序：

1. **止血（文档）**：被推翻的结论就地标注，对外材料的裁剪表述改回 CI 纪律措辞。这部分不依赖任何代码，先做。
2. **堵漏（代码）**：驱动侧接回库侧唯一实现 + 快照 digest 核验。这是「下次跑批 #112 原样复现」的唯一解，必须在下次烧 token 前落地。
3. **立规（规范 + 契约测试）**：把报告状态头与权威报告披露义务写成 requirement，配一条零成本的机器校验（路径可解析），使这套约束下次不用靠人记得。

### 为什么字段改名而不是「保留旧名 + 加注释」

`diff_median` 的值是均值差、配的 CI 也是 mean-diff 口径，唯独名字说中位数。在「同标的中位数配对」这个上下文里，读者很容易把 `diff_median` 理解成「中位数之差」——这正是消融报告被误读的通道之一。改名成本是两个消费点，收益是消除一个持续误导源。保留旧名再加注释等于把注释当防线，与「判据从 LLM 自律搬到代码」「治理对象是机制而非人」的既有取向不一致。

### 为什么快照核验选择「显式失败」而不是「自动重建 / 自动冻结」

- **自动重建**（digest 变了就重取并覆盖登记值）：会让同一批次里前后 run 输入不同，而报告仍宣称「差异只可归因于编排」——把静默错误变成静默错误 + 假证据。
- **自动冻结**（digest 变了就拒绝续跑并提示重跑全批）：等价于本方案，但把决策权从人手里拿走了；跨交易日续跑是否可接受取决于「数据源是否已刷新」这一环境事实，代码判不了。
- **显式失败**：报错给出标的与两侧 digest，由人决定是重跑全批还是接受混批并在报告中声明。人做决定，但决定**必须显式做出**。

### 报告状态的落点选择

完整的结论注册表（全库扫描 docs/evals/ + 索引页徽章 + 状态迁移机）需要先盘清全库每份报告的真实状态，属于独立的取证工作量，放进后续 delta。本 delta 只覆盖 `evals/ablation/results/*.md`（消融结果报告，当前 1 份），并把契约写成 requirement——后续 delta 把范围扩到 `docs/evals/*.md` 时，契约不变、只是扫描根目录变宽，不需要重写规范。

**为什么权威报告（n10）不标 superseded**：n10 的数字本身没错（唯一权威的 n=10 批次），错的是**表述**——自称「修复后」而实际带着 #112 存活与未校准 judge，并且被 README 引用成了裁剪依据。所以 n10 的处理是**保持 active + 补适用口径披露**，而不是标 superseded。区分「数字作废」与「数字有效但适用口径未披露」，是这套机制能长期用下去的前提。

## 关键技术决策

### 驱动 → 库侧的调用形态

驱动当前把「哪些维度适用」的知识抄了一份（`if variant == "analysts" and dim != "report_relevance"`）。改法有两种：

- **方案 A（选）**：驱动直接调 `ablation_mod._applicable_dims(variant)`。不新增公开别名——该函数是既有测试（`tests/evals/test_ablation.py:95-107`）的断言对象，改名只会连带改测试而无收益；跨模块调用下划线名字的代价由「唯一实现」的收益抵偿。假件（测试用）必须提供同名属性，这恰好覆盖了 a86986a 记录的 mock 缺口模式（假件带 `run_judge`，而真模块换 `run_judge_mean` 时假件仍通过）——测试要证明「驱动真的在问库侧要维度集合」，而不是自说自话。
- 方案 B：把判分循环整体从驱动搬进库侧（`run_variant_once` 里顺带判分）。改动面更大，且驱动的「按 run 计量 token / 落材料 / 落 resume」职责与判分耦合后反而更难测。不选。

### digest 核验的插入点

核验发生在 `run_pilot` 的快照获取处：`snapshot = build_snapshot(ticker)` 之后、任何 run 之前。台账里已有 `snapshot_digests`（`resume.json`）。

```
digest = snapshot_digest(snapshot)
registered = snap_digests.get(ticker)
if registered is None:
    snap_digests[ticker] = digest          # 首次登记
elif registered != digest:
    raise RuntimeError(...)                 # 显式失败，输出标的与两侧 digest
```

注意顺序：当前代码是「首次登记」在 ticker 循环开头、构建却在 repeat 循环内——核验必须放在**每次构建之后**，否则又变成一次登记、多次不核。

### 字段改名的兼容面

`diff_median` 的消费点是 `tests/scripts/ablation_aggregate_90.py`（2 处，读旧工作树 `resume.json` 复算 90 批报告）。该脚本本来就在 `metrics.md` §3 登记为「跑新批次前需参数化」的遗留项，本 delta 只做字段名同步，不顺手改路径与阈值（不扩大改动面）。历史产物 JSON 在新代码下复算会 KeyError——这是**期望行为**（旧字段名不再被承认），在 `metrics.md` 登记切点。

## 不做的事（明确的边界）

- **不做结论注册表 / 索引页徽章 / 全库状态扫描**：需先盘清 `docs/evals/` 全库每份报告的真实状态（9 份日期报告 + 台账 + 模板），属独立取证的机械轮。本 delta 只立契约 + 覆盖消融结果目录。
- **不做跑批入口唯一化**（驱动变薄壳、判分与过滤全调库侧）：本 delta 只把**维度过滤**这一处拉回库侧（#112 的直接来源）。驱动整体瘦身会牵动计量、材料落盘、断点续跑三块，另立 delta。
- **不做阳性对照进跑批**（每轮消融带已知劣化变体，测不出差异则本轮阴性结果作废）：这是防「评估系统失灵导致的假阴性」的机制，需要先定「已知劣化变体」的构造与判定阈值，属评估框架层设计。
- **不重跑任何跑批**：本 delta 只改口径实现与文档，不烧 token。n10 数字继续作为权威（补披露后）。
- **不改 README 以外的对外材料**：简历素材由 owner 自行处理，本 delta 只保证仓库内的材料不再陈述被推翻的结论。

> 上述四项（注册表 / 入口唯一化 / 阳性对照 / v2 消融框架的因果主张登记 + 注入法 + 单元级判定）构成「评估补强」的后续批次，与本 delta 互补：本 delta 修的是「已有结论的可信度管理」，它们修的是「新结论的产出机制」。

## Risks

- **改名破坏历史产物复算**：历史 `reports/ablation/pilot-*.json`（本地未入库）字段名与新代码不符。对策：`metrics.md` 登记切点；数字本身不受影响。
- **digest 核验误伤正常续跑**：若某标的的快照 digest 天然不稳定（如含时间戳/随机序），核验会让正常续跑直接失败。对策：`snapshot_digest` 只哈希 DataFrame 的 `tobytes()` 与标量值，K 线/指标为确定性数据；本 delta 的测试覆盖「同快照两次 digest 相等」与「不同快照 digest 不等」两侧，先证明 digest 本身可比。
- **披露过重导致报告不可读**：口径披露堆在头部会淹没结果。对策：头部落 3-4 行要点 + 结论区就地标注关键条目，不做成独立长章。
