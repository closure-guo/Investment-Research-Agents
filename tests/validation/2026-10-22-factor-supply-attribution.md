## 3. 实验 A：横截面 z-score / rank 对闸门读数不变

`zscore(x)` 与 `rank(x)` 是逐日横截面单调变换，而五道闸用的是 **RankIC**
（[validate.py](src/finance_agent/factors/validate.py)），逐日秩不变 ⇒ IC 序列应逐位相同。

实测（500 日面板，`x = sub(div(close,ref(close,5)),1)`）：

| 表达式 | n | mean IC | std | ICIR |
|---|---|---|---|---|
| `x` | 494 | -0.03804574 | 0.15929985 | **-0.23883100** |
| `zscore(x)` | 494 | -0.03804574 | 0.15929985 | **-0.23883100** |
| `rank(x)` | 494 | -0.03804574 | 0.15929985 | **-0.23883100** |

IC 序列 `Series.equals()` 均为 `True`。**结论：CSZ 变体不会比它的内层因子更容易过闸**；
补 CS 合约能提升覆盖与可审计性（+67 条左右），但不会因为「做了横截面标准化」而提高入库率。
真正携带新信息的是 16 条需要横截面均值/协方差、滚动回归或 PCA 的候选——那需要新算子，成本高。

## 6. 结论

1. 零入库不是管道故障、不是断供；是**候选强度（主要矛盾）+ 表达面结构（覆盖）+ 吞吐与重复（效率）**三者叠加。
2. 闸门：105 条卡闸②、16 条卡闸④、6 条卡闸⑤，读数自洽且与历史验证一致；**不建议为产出而降阈值**。
3. 表达面：84 条截面向拒译是**转译合约限制**（Qlib-only 输出），不是 DSL 能力缺失；
   但按 RankIC 不变性，修合约主要买覆盖率，不买入库率。
4. 重复：41% 的过闸调用花在重复表达式上（`mom20`/`mom_20d`/`MOM_20D`/`momentum_20d` 等跨会话反复提案）；积压 459 条未裁决。
5. 结构性事实：RD-Agent 当前产出集中在动量/反转/波动/区间四族（价量低阶矩），
   与池内 4 个因子高度同源——**供给侧方向**才是决定入库率的上游变量。

## 7. 建议（按杠杆排序，均需单变量验证）

1. **供给改向**（最高杠杆）：换研究起点（研报/异象知识库驱动）、把「已否决表达式 + 拒因」回喂
   RD-Agent（项目内 `propose.py` 已有拒收回喂先例），减少同族重复探索。
2. **去重的位置要选对**（§9 实测）：候选级文本/签名去重不可安全自动化；
   **转译后、过闸前**按 DSL 去重可安全回收 41% 的闸门调用（不省 LLM 名额）；
   根本解法仍是把已探索表达式注入生成侧，避免同一经典因子跨会话反复提案。
3. **提高裁决吞吐**：日批 → 多次/日（每批 K≤100 的 BH-FDR 约束不变），先清 459 条积压；
   不改单批上限。
4. **CS 合约扩展（低风险、中收益）**：允许 `CSZScore(x)`/`CSRank(x)`（映射到现有 `zscore`/`rank`），
   顺带补 `cs_demean`；预期 +67 条覆盖，不承诺入库增量，价值在可解释性与覆盖率。
5. **不建议**：调整 `MIN_ABS_ICIR` / `MAX_IC_CORRELATION`——已有两组「降尺子 0 入库」实证。

## 9. 补充实验 C：去重前置能清出多少名额

**C1 文本近重复（描述词集 Jaccard，阈值在真值上标定）**

- 真值：140 条有 DSL 的候选里 101 对同义（含 epsilon 归一），57 条重复行；
- 描述 Jaccard 在 0.75–0.95 全域 F1 ≈ 0.02，最高命中 1 对；
- 积压 463 条中「与已处理重复」0 条、批内重复 2 条 → 可回收 **2 条（0.4%）**。
- 原因：同一因子被跨会话**改写文案**——`mom20` / `mom_20d` / `MOM_20D` / `momentum_20d`
  四条 DSL 完全相同、描述各不相同；`vol_20d` / `REALIZED_VOL_20D` / `VOL_20D` / `Vol20` 同理。

**C2 结构签名（因子族 + 窗口集合 + 字段集合）**

- 在 140 条真值上：precision **0.688**、recall **0.436**（候选对级）；
- 误伤实例：`IntradayRet1`（(close-open)/open）与 `Gap1`（open/prev_close-1）同签名但不同因子；
  另有若干「误伤」实为代数等价（`1-x` 与 `0-(x-1)`），说明真值本身低估了重复；
- 积压上限：签名命中已处理 147 条 + 批内 37 条 = **184 条（39.7%）**，
  但按 precision 0.69 计，直接自动化会误删约三分之一不同表达式。

**C3 结论**

| 去重点 | 可回收 | 是否安全 | 说明 |
|---|---|---|---|
| 候选级文本 | 2/463 = 0.4% | 安全但几乎无效 | 文案被改写 |
| 候选级签名 | ≤184/463 = 39.7% | **不安全**（p≈0.69） | 会删掉 intraday vs overnight 这类不同因子 |
| 转译后 DSL | 57/140 = 41% 闸门调用 | 安全 | 只省闸门算力，不省每日 60 个 LLM 名额 |

- 生成侧不记忆已探索因子是重复的根源；harvest 侧去重只能治标。
- 建议落地：`run_factor_harvest` 在 `run_factor_external_import` 前按 DSL 表达式去重
  （保留首条并记 `duplicate_of`），减少闸门调用与账本噪声；LLM 名额问题回到供给侧解决。
