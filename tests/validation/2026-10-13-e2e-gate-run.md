## 修复记录（2026-10-13 后续处置）

### 修复 1（已修，已复验）：战绩页套件本地重跑脏库误红

- **根因**：该套件多 spec 假设「库内只有自己造的行」（`track-record-pred-tabs` 空态前提、duplicates 行唯一断言等）；`track_record_reset` 旧语义只清 `equity_curve + paper_equity`，残留的 `predictions`（实测 49 条）/`daily_marks` 令本地重跑必红（CI 每次全新起库不受影响，config 注释原已要求「本地重跑前手动删库」）。
- **修复**：
  1. 新增 `delete_all_track_record_state()`（predictions/daily_marks/equity_curve/agent_metrics_daily/index_closes 五表，单事务、幂等；不动 agents/audit_log/risk_free_rates），`track_record_reset` 语义扩为**全量复位**（含 paper_equity）；
  2. 该 config 增加 `globalSetup`（`global-setup-track-record.ts`）经 TESTING 端点自动全量复位——**Playwright 1.62 实测 webServer 先于 globalSetup 启动**（探针 `serverUpDuringGlobalSetup: true`），故可直接 HTTP 复位；
  3. 同步更新受影响断言（`tests/test_api_track_record.py` 的复位边界由「predictions 原样保留」改为「一并清空」，文档化契约变更）+ 新增模型层单测；`ui-baseline-pages.spec.ts` 的复位注释同步更正。
- **复验**：**连续两轮不清库跑套件 → 16/16、16/16**（第二轮正是此前必红的脏库场景）；`uv run pytest tests/outcome tests/test_api_track_record.py -q` → 606 passed；ui-baseline 14/14（复位语义扩大未影响像素基线）。提交 `580849b0`。

### 修复 2（部分修，根因已定位并立 issue）：时间轴「运行中瞬态」族抖动

- **复现**（`--retries=0` 全量 timeline 套件）：基线 **2 failed / 32 passed**（`pipeline-hierarchical-timeline` 1、`thinking-timeline-pipeline` 1）。
- **证据链**（trace 保留于 `tmp/e2e-artifacts-repro/`）：
  1. `POST /api/analyze` 为 `text/event-stream; chunked`，**流开着 29.4s** 覆盖整个 stub 管线，无 console 错误；
  2. screencast 帧：应用已进入分析视图并渲染思考/工具横幅，随后**两帧相隔 18 秒逐字节相同**（深析阶段 UI 全程冻结），流结束后才跳到完成态报告；
  3. 断言等待的「运行中」元素（timeline 挂载点 / ETA 文本 / PipelineCard 分组）在整个窗口内不存在 → 超时。
- **排除项**：加宽运行窗（`STUB_NODE_DELAY` 1.5→3，窗口 15s→30s）实测仅把抖动从 2 降到 1 且套件时间 +60%，失败态 UI 仍整段未渲染运行态 → **非窗口长度问题，已回退该改动**。
- **处置**：根因指向 **SSE relay/journal 投递在高 CPU 争用下成批延迟/被饿死**（与 incident 039 relay-lag、#266、#265 同族；对真实用户的影响=负载机器上观看运行中分析会长时间停在「思考中」）→ 立 **issue #328**（含复现命令与时延埋点建议）。E2E 侧保留 `global-setup-timeline.ts` 预热三前端（降低 vite 冷启动 20–30s 的既有风险，其对本族抖动的效果未获证明，仅为冷启动卫生）；CI 门禁 `retries=1` 继续吸收该族（历史先例 #312）。
- **回退后最终门禁口径复验**（`retries=1`，本机当时负载显著偏高，套件 15.3m vs 首轮 8.0m）：**1 failed（`pipeline-eta-banner` 1，两次尝试均失败）/ 3 flaky（重试通过）/ 30 passed / 1 skipped**。失败者仍属同一既有族（非本分支引入：该族 2026-10-02 已有记录、issue #312 已挂）；本机已确认无残留进程（`tasklist`/`netstat` 干净），故差异来自机器负载而非环境残留。
- **结论（修复 2）**：E2E 侧可做的都做了（排除窗口长度、保留冷启动卫生）；族根因在产品侧流投递时延，须由 **issue #328** 的埋点排查收口。断言强度未削弱（红线保持）。
